1. Introduction

1.1 Purpose

This document defines the software requirements for Kottayam Online Judge (KOJ), version 1.0.
KOJ is a web-based competitive programming platform that supports problem hosting, code
submission, automated judging, and contest management. It is designed for use by IIIT Kottayam
students and faculty for conducting programming contests and practice sessions.
This SRS covers the complete system including the web frontend, the backend API, the judge
engine, and the database.

1.2 Document Conventions

    •   Requirements are identified with unique IDs in the format REQ-<CATEGORY>-<NUMBER>
        (e.g., REQ-AUTH-01).
    •   Priority levels: High (must have for v1), Medium (should have, may defer to Phase 2), Low
        (nice to have).
    •   This document follows the IEEE 830-1998 standard for Software Requirements
        Specifications.
    •   All timestamps use IST unless otherwise stated.

2. Overall Description

2.1 Product Perspective
KOJ is a self-contained web application built as a new product, not a replacement for or extension
of an existing system. It is designed as a three-tier architecture with clear separation between the
presentation layer, application logic layer, and data layer.


The frontend communicates with the backend through REST API calls and WebSocket connections.
Authentication is handled by Clerk, which manages user sessions, OAuth providers (Google,
GitHub), and JWT token verification. The backend handles all logic, dispatches code judging to an
isolated subprocess, and reads/writes data to Neon (PostgreSQL). The judge engine runs as a
subprocess spawned by the backend, with no direct access to the database or the frontend. Realtime
verdict and leaderboard updates are delivered via FastAPI WebSocket connections.
This separation is deliberate. The judge module is loosely coupled from the web layer. The API
does not know how the judge works internally; it only calls a function that returns a verdict. This
lets us test the judge in complete isolation and replace its implementation without affecting the rest
of the system.

Architectural styles used:
Style       Where in KOJ                              Why it is used
                                                      Each request passes through all three layers
Layered      Frontend -> API -> Database              with no skipping
Pipe-and-    Judge pipeline: receive -> compile ->    Each stage has one job and a fixed input/output
Filter       execute -> check -> verdict              contract
Event-       FastAPI WebSocket pushes verdict         Backend writes verdict, pushes update to UI
Driven       changes to connected clients             via WebSocket, no polling required
Master-      FastAPI (master) dispatches to judge     Subprocess has no awareness of the web layer
Slave        subprocess (slave)

Coupling and cohesion decisions:

- The judge module is highly cohesive (does exactly one thing: take code + input, return verdict)
and loosely coupled (the web layer calls it via a clean interface and does not care how it runs code
internally).
- The contest module and problem module are deliberately decoupled. A problem does not know
which contest it belongs to at the problem-object level; the contest holds references to problems.
This allows problems to exist independently after a contest ends (the archive feature).
- A naive design would tightly couple Contest and Problem. We rejected that because it would make
post-contest practice impossible without duplicating problem data.

2.2 Product Functions
The major functions of KOJ are:
   • User Registration and Authentication: Users sign up with email/password or OAuth
      (GitHub, Google). Three roles: Contestant, Problem Setter, Admin.

    •   Problem Management: Problem setters create problems, upload test cases (input/output

    •   Contest Management: Admins create contests, add problems, set start/end times, choose
        between open enrollment or invite-based registration.
    •   Code Submission: Contestants select a problem, write code in the browser or paste code,

    •   Rate Limiting: Submissions are throttled to prevent abuse (max 1 submission per 30

2.5 Design and Implementation Constraints

    1. Budget: The project must run within free tiers and Azure student credits. No paid
       infrastructure beyond what student credits provide.
    2. Team size: 4 developers.
    3. Sandboxing: KOJ uses process-level isolation via Python's resource module (rlimit)
       instead of Docker containers. This is sufficient for a trusted college user base but not for
       open internet deployment. A Docker-based upgrade path is documented for v2.
    4. No interactive problems in v1: Only problems with static input/output test cases are
       supported.
    5. Single time limit per problem: No per-language time limit multipliers (Python submissions
       will be harder to pass at tight time limits, same as on SPOJ).
    6. Leaderboard consistency model: The leaderboard uses a push-based model via
       WebSocket. The backend writes the verdict to the database and immediately pushes the
       update to connected clients. This gives sub-second propagation without depending on a
       third-party realtime service.
    7. Future Enhancement (v2): The judge will employ container-based sandboxing (e.g.,
       Docker) or OS-level isolation mechanisms (such as namespaces/seccomp) to enforce
       filesystem isolation and stronger security.

3. External Interface Requirements

3.1 User Interfaces
The system provides a web-based interface accessible through standard browsers. Key screens
include:
    • Home Page: Shows recent problems, active contests, and user stats.
    • Problem List: Filterable list of all problems with status indicators (solved/unsolved).
    • Problem View: Problem statement, code editor (or textarea), language selector, submit

The UI follows a clean, minimal design similar to Codeforces. No complex animations or heavy
visual effects. Responsive design for desktop and tablet (mobile is not a priority for v1).

KOJ does not interface with any specialized hardware. It runs on standard cloud VMs or local
machines. The backend server should have at least 2 CPU cores and 4 GB RAM to handle
concurrent judging.

Frontend to Backend: REST API over HTTPS. JSON request/response format.

4.3 Code Submission and Judge Pipeline

4.3.1 Description and Priority
This is the core feature of KOJ. A contestant submits code, and the system compiles (if needed),
executes, and evaluates it against all test cases for the problem. The judge runs as a separate
subprocess, completely decoupled from the web layer. Verdicts are returned in real time.
Priority: High
The judge pipeline follows a pipe-and-filter architecture:
Receive -> Compile -> Execute -> Check -> Verdict
Each stage has a single responsibility:
    • Receive: Accept source code, language, and problem ID.
    • Compile: Translate source code to executable (skipped for interpreted languages like
        Python).
    • Execute: Run the executable with test case input, enforcing time and memory limits.
    • Check: Compare output against expected output (whitespace-normalized string comparison
        in v1; custom checker in v2).
    • Verdict: Return AC (Accepted), WA (Wrong Answer), TLE (Time Limit Exceeded), MLE
        (Memory Limit Exceeded), RE (Runtime Error), or CE (Compilation Error).

4.3.2 Stimulus/Response Sequences
    1. Contestant selects a problem, writes or pastes code, selects a language, and clicks "Submit."
    2. System validates the submission (checks language is supported, code is not empty) and
        returns HTTP 202 Accepted with a submission ID.
    3. Backend enqueues the submission for judging.
    4. Judge subprocess receives the source code and test cases.
    5. If the language requires compilation (C, C++, Java), the judge compiles the code. If
        compilation fails, verdict is CE.
    6. Judge executes the compiled binary (or interprets the script) with each test case as stdin,
        enforcing time limit (wall-clock) and memory limit (rlimit).
    7. If execution exceeds time limit, verdict is TLE. If memory limit is exceeded, verdict is
        MLE. If the process crashes or returns non-zero exit code, verdict is RE.
    8. For each test case, judge compares output against expected output using whitespace-
        normalized string comparison.
    9. If all test cases match, verdict is AC. If any test case fails, verdict is WA.
    10. Backend writes the verdict to the database.
    11. Backend pushes the verdict to the contestant via WebSocket.
    12. Contestant sees the verdict update in real time without refreshing the page.

4.5 Live Leaderboard

4.5.1 Description and Priority

The leaderboard shows a real-time ranking of contestants in a contest. Rankings are based on
problems solved (descending) and penalty time (ascending). Penalty is calculated as: time of first
accepted solution (in minutes from contest start) + 20 minutes per incorrect submission before the
first AC.
Priority: High

4.5.2 Stimulus/Response Sequences
    1. Contestant submits code during a live contest.
    2. Backend judges the submission and writes the verdict to the database.
    3. Backend pushes the updated leaderboard to all connected clients via WebSocket.
    4. Frontend receives the update and recalculates the leaderboard.
    5. All connected clients see the updated ranking without refreshing the page.

6. Other Requirements
    1. Database: All persistent data shall be stored in Neon (PostgreSQL). The schema shall
       include tables for users, problems, test_cases, submissions, contests, contest_problems,
       contest_registrations, and leaderboards.
    2. Logging: The backend shall log all judge executions (submission ID, language, verdict,
       execution time, memory usage) for audit and debugging purposes.
    3. Deployment: The system shall support one-command deployment via Vercel (frontend) and
       Azure App Service / GCP Cloud Run (backend). Environment variables shall be
       configurable through each platform's dashboard.
    4. Version Control: The project shall use Git with a feature-branch workflow. All code shall
       be hosted on a shared GitHub repository.
    5. Future Enhancements (v2): Custom checker programs via testlib.h, interactive problems,
       Docker-based sandboxing, per-language time limit multipliers, Redis caching layer,
       automated test case validation.
